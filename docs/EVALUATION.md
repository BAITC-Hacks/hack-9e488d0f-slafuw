# Проверка качества и Definition of Done

## 1. Матрица требований

| Требование трека | Реализация | Как проверяем |
|---|---|---|
| Все обязательные и опциональные входы | `Request.parse`, форма | Валидные/ошибочные типы, null, опущенные поля |
| До 3 карточек | `eligible[:3]` | Плотный запрос с 7 допустимыми и проверки на 100 датах |
| Имя, категория, город, цена, объяснение | `make_card` | Ответы API и ручной просмотр UI |
| Занятые не попадают | `failures: busy` | Независимый field-based oracle на 100 датах |
| Площадки имеют такой же календарь | Общее ядро | Залы на 14 ноября, исключение занятого зала |
| Меньше 3 — число и причина | `summary`, диагностика | Флористы: 2 из 2; залы: 2 из 7 |
| Детерминированный порядок | Полный ключ и неизменяемые данные | Повтор, обратный порядок каталога, subprocess с разными hash seeds |
| Три различимых исхода | `status`, три заголовка UI | HTTP 200 для двух видов пустоты и для подбора |
| Пустой результат объяснён | Сводка + причины + подсказки | `04-busy`, `05-no-category`, `07-budget` |
| Две даты дают разную выдачу | Только календарь меняет допуск | 12/13 октября, Сон Гоку появляется после занятой даты |
| Объяснения не взаимозаменяемы | Факты + уникальные основания | Автопроверка строк без имён + обязательный ручной тест |
| До 10 секунд | In-memory ядро | Benchmark ядра, HTTP smoke, ручной полный путь |
| Команда объясняет пайплайн | Документы и trace | Репетиция по `DEMO.md` |

Наличие теста отдельной функции ещё не доказывает удобство живого интерфейса. Последний этап — показать весь путь ввода и чтения результата человеку.

## 2. Выполненные автоматические проверки

Команда:

```console
python -X utf8 -m unittest discover -s tests -v
```

Текущий набор — **22 теста**:

- 18 тестов данных, бизнеса, источников, детерминизма и проверенных подсказок;
- 4 интеграционных HTTP-теста, включая форму/metadata, живой подбор, бизнес-пустоту и ошибочный JSON.

Важные проверки:

1. **Oracle по полям** независимо от функции `failures` пересчитывает допустимое множество на каждом из 100 дней для ведущих Алматы.
2. **Равенство на границе:** 500 000 ₸ допускает Куррапику, 499 999 ₸ — нет; часы 6 допустимы, 6,5 исключают профиль с максимумом 6.
3. **Неоднозначность описания:** Кики не допускается к конференции, несмотря на упоминание её в тексте.
4. **Причинность даты:** Сон Гоку исключён 12 октября только из-за занятости и входит в тройку 13 октября.
5. **Источник:** срез исходного текста в точности совпадает с цитатой всех демокарточек.
6. **Перезапуск:** результаты CLI идентичны при `PYTHONHASHSEED=1` и `99`.
7. **Counterfactual:** подстановка ровно одного предлагаемого изменения действительно даёт заявленное число допустимых кандидатов.

Не утверждаем, что эти тесты перебирают все возможные комбинации городов, категорий, форматов, бюджетов и длительностей.

## 3. Инварианты для дальнейшей разработки

| Инвариант | Допустимое значение |
|---|---:|
| Нарушения обязательных условий в карточках | 0 |
| Дубли ID внутри выдачи | 0 |
| Максимум карточек | 3 |
| Точные цитаты, подтверждённые источником | 100% |
| Изменение порядка при неизменных данных/политике/запросе | 0 |
| Ошибочная классификация no-category / no-match | 0 на контрольном наборе |
| Ложные подсказки изменения одного условия | 0 |

AI-слой должен проходить эти же инварианты. Улучшение среднего текста не компенсирует пропуск занятого подрядчика.

## 4. Ручная оценка объяснений

### Почему недостаточно проверять уникальность строк

Три текста могут отличаться ценой или случайным словом и при этом ничего не объяснять. Совпадение с источником также не означает полезность: цитата «Мы создаём впечатления» точная, но не помогает выбирать.

### План набора

Подготовить **24 запроса**: 16 development и 8 holdout, с заранее сохранёнными параметрами. Набор должен включать плотные категории, редкие категории, площадки, обе пустые ситуации, разные даты и запрошенные язык/часы.

Для оценки ранжирования отбирать отдельную подвыборку, где после фильтрации **больше трёх** кандидатов. При одном свободном флористе оценивать полноту объяснения, но не заявлять улучшение ранжирования.

Изменять правила и промпты по development; holdout использовать для итогового сравнения. Два оценщика сначала работают независимо, затем разбирают разногласия. Это экспертная оценка на небольшом наборе, не статистическое доказательство пользовательской конверсии.

### Рубрика карточки, 0–2 по каждой оси

| Ось | 0 | 1 | 2 |
|---|---|---|---|
| Основания | Выдуманный/противоречивый факт | Частично подтверждено или двусмысленно | Все утверждения имеют корректный источник |
| Связь с запросом | Общая реклама | Одно общее совпадение | Конкретная связь с форматом/условиями |
| Различимость | Можно переставить текст к любому | Отличается в основном числами | Есть полезная особенность именно этого профиля |
| Ясность | Перегружено или непонятно | Понятно после внимательного чтения | 1–2 ясные фразы, понятен компромисс |

**Плановый порог приёмки:** ноль выдуманных фактов; каждое объяснение с оценкой 2 по основаниям; среднее не ниже 6/8; не менее 90% оценённых карточек имеют содержательно различающее основание. Это цели, а не уже измеренный результат.

### Слепой тест из Definition of Done

1. Выбрать запрос с тремя карточками.
2. Удалить имена, ID и названия, которые просто повторяют идентификатор.
3. Отдельно показать три профиля и три перемешанных объяснения.
4. Попросить сопоставить и назвать факт, на котором основано соответствие.
5. Ошибки из-за взаимозаменяемого текста отправить в backlog выбора evidence.

Просто заменить слова «профессиональный» на «опытный» не является исправлением.

## 5. Сравнение алгоритмов

Проверить три режима при одинаковых жёстких фильтрах:

- A: цена по возрастанию + ID; объяснение только структурированными фактами.
- B: текущий lexical baseline + extractive-цитаты.
- C: плановый AI evidence/semantic, после его реализации.

Сравнение должно разделять две задачи:

1. **Качество объяснений:** слепая рубрика, groundedness, различимость, ясность.
2. **Качество порядка:** оценки релевантности кандидатов 0–2 от оценщиков; NDCG@3 на плотных запросах, если такая разметка собрана.

Отдельно проверить абляцию «B без цитат» и «C без AI-перестановки», чтобы понять, даёт ли пользу объяснение, ranker или оба. Не публиковать NDCG и проценты улучшения до реального измерения.

## 6. Производительность

```console
python -X utf8 -m tools.benchmark
```

Скрипт загружает каталог, прогревает семь запросов, выполняет каждый 50 раз и сохраняет `data/reports/benchmark.json`.

Сохранённый локальный результат: Python 3.12.8, Windows, 350 вызовов, p50 0,403 мс, p95 1,583 мс, max 5,029 мс, загрузка каталога 4,106 мс. Повторный запуск обновляет измерения и зависит от машины/нагрузки.

Это замер **ядра**, а не HTTP latency. HTTP-интеграционные тесты имеют timeout 5 секунд, но не являются нагрузочным benchmark.

Перед защитой измерить отдельно:

- время холодного старта сервиса;
- полный запрос браузер → API → карточки;
- самый длинный текст/плотную категорию;
- пустой запрос с вычислением подсказок;
- если появился AI — холодный и прогретый режим, отсутствие сети и ключа.

Цель трека — до 10 секунд; для текущего offline-ядра разумная внутренняя цель полного локального пути — менее 1 секунды. Обе формулировки являются целями полного пути, не подменяются измерением чистой функции.
