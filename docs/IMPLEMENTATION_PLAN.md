# Подробный план реализации и доведения до защиты

## 0. Цель и исходная точка

**Цель хакатона:** показать живой сервис, который из заданного каталога возвращает до трёх допустимых подрядчиков, помогает понять их различия и объясняет отсутствие результата.

**Исходная точка этого репозитория:** рабочее ядро, API, минимальный UI, полный набор данных, аудит, семь демозапросов и 22 теста уже существуют. План ниже одновременно служит:

- пошаговой картой решения с нуля для команды;
- backlog следующей итерации поверх готового baseline;
- системой приёмки перед выступлением.

Оценки времени — ориентиры для команды из 2–3 человек. Не следует тратить сутки на повторную реализацию уже работающих частей.

## 1. Что должно быть готово к концу

### Обязательный результат P0

- [x] Пять обязательных входов и два опциональных.
- [x] Строгий город и точная категория.
- [x] Занятых на выбранную дату нет в выдаче.
- [x] Язык, часы, формат и бюджет проверяются одинаково для всех категорий.
- [x] Площадки используют тот же календарный механизм.
- [x] Не более трёх уникальных карточек.
- [x] Три отдельные бизнес-ситуации явно видны в UI/API.
- [x] Объяснения содержат реальные поля/цитаты, а не общую похвалу.
- [x] Синтетика и проставленные поля видны пользователю.
- [x] Повтор, перезапуск и перестановка входных записей не меняют ответ.
- [x] Реальные демонстрационные запросы сохранены и проверяются кодом.
- [x] Репозиторий запускается без ключей и скачивания моделей.
- [ ] Проведена слепая человеческая оценка различимости объяснений.
- [ ] Завершена ручная проверка браузера и репетиция защиты.

### Усиление P1

- [ ] Содержательные признаки профиля с проверяемыми источниками.
- [ ] AI-подбор наиболее релевантных и различающих оснований.
- [ ] Измеренное сравнение baseline / AI на отложенных запросах.
- [ ] Более короткое, контрастное объяснение: главная особенность + совпадение условий.
- [ ] Автоматический анализ изменения состава между двумя датами.

### Развитие P2

- [ ] FastAPI/OpenAPI и публичный пилот.
- [ ] Дополнительный текст пожеланий при сохранении обязательного сценария.
- [ ] AND-поддержка нескольких требуемых языков.
- [ ] Производственная наблюдаемость, обновление календаря и каталога.
- [ ] Обратная связь о полезности рекомендаций и разметка качества.

## 2. Рабочий план на 24 часа

| Окно | Этап | Основной результат | Критерий завершения |
|---|---|---|---|
| 00:00–01:00 | Разбор трека | Таблица требований, границы продукта | Команда одинаково трактует цену, null, дату и три исхода |
| 01:00–03:00 | Данные | Типизированный каталог, манифест, аудит | 66 записей проходят схему; распределения и hash сохранены |
| 03:00–06:00 | Доменное ядро | Фильтры, статусы, диагностика | Ни один нарушитель не проходит; подсчёты сходятся |
| 06:00–09:00 | Карточки и объяснения | Ранжирование, evidence, две фразы | Каждое утверждение имеет источник; есть различия карточек |
| 09:00–11:00 | Сквозной сценарий | API, форма, реальные запросы | Пользователь получает все три исхода в работающем UI |
| 11:00–15:00 | AI-усиление | Офлайн признаки/эмбеддинги | Артефакт валиден и версия фиксирована; baseline остаётся контрольной линией |
| 15:00–18:00 | Оценка | Автотесты, слепая оценка, сравнение | Нет нарушений, тексты лучше или AI не включается в основной режим |
| 18:00–20:00 | Воспроизводимость | Финальный README, CI, снимки | Запуск на чистом окружении по README без устных инструкций |
| 20:00–22:00 | Защита | Репетиция, контроль дат и ограничений | Живой показ за 4–5 минут без заготовленных «ответов вместо вычисления» |
| 22:00–24:00 | Резерв | Исправления дефектов, фиксация версии | Новые крупные функции не нарушают готовую демонстрацию |

Для текущего состояния наиболее полезны этапы **11:00–18:00 и 20:00–22:00**, а не переписывание фильтрации.

### Распределение ролей

- **Backend/data:** схема, календарь, фильтры, диагностика, API, воспроизводимость.
- **AI/explanations:** признаки, цитаты, выбор оснований, сравнение вариантов, качество текста.
- **Product/QA/demo:** форма, реальные сценарии, независимая разметка, документация, выступление.

Для двух участников: первый совмещает backend/data и HTTP, второй — explanations и product; проверку качества выполняют оба независимо. Для одного: P0 → объяснения → репетиция, затем P1 в пределах оставшегося времени.

## 3. Задачи с зависимостями и критериями приёмки

### T01 · Зафиксировать контракт задачи — P0, 30–60 мин

**Действия:**

1. Перевести требования трека в проверяемые условия.
2. Зафиксировать: бюджет на подрядчика; часы его работы; один язык; дата внутри окна.
3. Разделить бизнес-пустоту и неверный запрос.
4. Зафиксировать приоритет структурированных полей над описанием.

**Артефакты:** `docs/SOLUTION.md`, `docs/API.md`, матрица в `docs/EVALUATION.md`.

**Приёмка:** для любого из трёх исходов можно назвать точное условие кода, а не решение модели. В текущей версии выполнено.

### T02 · Подготовить каталог — P0, 1–2 ч, после T01

**Действия:**

1. Прочитать CSV с учётом кавычек и Unicode.
2. Конвертировать списки, boolean, цену, null-часов.
3. Проверить уникальность ID, календарь, обязательные поля.
4. Сохранить канонический JSONL и SHA-256.
5. Посчитать матрицу категория/город, календарные доли, флаги.
6. Отдельно записать противоречия свободного текста.

**Артефакты:** `tools/import_dataset.py`, `tools/audit.py`, `data/raw/`, `data/manifest.json`, `docs/DATA_AUDIT.md`.

**Приёмка:** 66 профилей; 13 синтетических; 50/15/1 по городам; нет потери дат и флагов. В текущей версии выполнено.

### T03 · Реализовать допуск и исходы — P0, 2 ч, после T02

**Действия:**

1. Сначала определить круг `city + category`.
2. Для каждого профиля вычислить все причины отказа.
3. Разрешить равенство бюджета цене и часов максимуму.
4. Не применять часы к `null`, но всегда применять дату.
5. Вернуть правильный статус и число прошедших.

**Приёмка:** независимый oracle совпадает с ядром на всех 100 днях контрольного запроса. Отдельные проверки для площадки, null, языка и противоречия текста/полей. В текущей версии выполнено.

### T04 · Сделать воспроизводимое ранжирование — P0, 1 ч, после T03

**Действия:**

1. Начать с открытого ключа `(-relevance, price, id)`.
2. Зафиксировать словарь baseline и версию.
3. Не добавлять одинаковые баллы за уже обязательные совпадения.
4. Не сортировать по числу занятых дат, synthetic или «премиальности» цены.

**Приёмка:** запрос с >3 допустимыми действительно выбирает тройку; повтор и перезапуск совпадают; точные равенства разрешаются по ID. В текущей версии выполнено.

### T05 · Создать объяснения с evidence — P0, 2–3 ч, после T03/T04

**Действия:**

1. Построить объекты фактов для цены, даты, формата, языка, часов.
2. Найти различающие фрагменты описания.
3. Сохранить источник, координаты, точную цитату.
4. Сформировать два предложения без придуманных качеств.
5. Отдельно показать происхождение данных и значение «от».

**Приёмка:** цитата побайтно после декодирования совпадает с соответствующим срезом строки; все цифры из полей; имена не являются единственным отличием объяснений. Автопроверка выполнена на демо; слепая человеческая проверка ещё нужна.

### T06 · Объяснить пустую выдачу — P0, 1–2 ч, после T03

**Действия:**

1. Сформировать непересекающиеся основные причины и полный список нарушений.
2. Считать отдельно кандидатов, исключённых только из-за даты.
3. Проверять контрфактуалы изменением одного поля.
4. Не писать «все заняты», если часть не проходит по другим условиям.

**Приёмка:** каждую показанную подсказку можно отправить как новый запрос и получить указанное число прошедших. В текущей версии выполнено для даты и бюджета.

### T07 · Дать сквозной интерфейс — P0, 1–2 ч, после T03/T05/T06

**Действия:**

1. Реализовать `POST /recommend` и metadata.
2. Форма: 5 обязательных полей + 2 опциональных.
3. Карточка: имя, категория, город, цена, объяснение, метки.
4. Состояния загрузки, понятной ошибки, пустой выдачи.
5. Кнопки контрольных запросов; раскрываемые evidence/диагностика.

**Приёмка:** ни одна ситуация не даёт пустой экран; исходы имеют разные заголовки; нет дублирования бизнес-логики в JS. HTTP реализован и протестирован; визуальная проверка остаётся перед защитой.

### T08 · Подготовить AI-признаки — P1, 2–3 ч, после T02/T05

**Действия:**

1. Выделить стабильные spans и их IDs.
2. Выполнить офлайн LLM-извлечение типов признаков и IDs оснований.
3. Валидировать IDs, типы, description hashes, пустые ответы.
4. Признаки противоречащие структурированным условиям не использовать для допуска.
5. Сохранить артефакт и версию модели/промпта.

**Плановые файлы:** `tools/build_features.py`, `eventmatch/features.py`, `data/derived/profile_features.jsonl`.

**Приёмка:** каждый пригодный признак имеет существующий источник; артефакт не меняется при обычном запуске; отсутствие ключа на машине жюри не мешает работе. Ещё не реализовано.

### T09 · Подключить семантический выбор оснований — P1, 1–2 ч, после T08

**Действия:**

1. Выбрать одну готовую multilingual-модель и зафиксировать revision.
2. Подготовить эмбеддинги фрагментов и ограниченного набора намерений.
3. Сохранить квантованные оценки.
4. Сначала улучшать выбор объяснений, затем отдельно тестировать изменение ранжирования.
5. Экспортировать версию и режим в метаданные.

**Плановые файлы:** `tools/build_semantics.py`, `eventmatch/semantic.py`, артефакты в `data/derived/`.

**Приёмка:** разные описания получают осмысленные основания; порядок детерминирован; сравнение не показывает ухудшение; семантика не пропускает занятых или дорогих кандидатов. Ещё не реализовано.

### T10 · Провести оценку — P0/P1, 2–3 ч, после T05/T09

**Действия:**

1. Выполнить автоматические инварианты и HTTP-тесты.
2. Подготовить 24 запроса: 16 для разработки, 8 отложенных для сравнения.
3. Включить разные категории, города, осень/декабрь, пустые случаи, ограничения языка и часов.
4. Двум участникам независимо оценить факты, полезность и различимость текстов.
5. Сравнить минимум две линии: цена+правила и текущий baseline; при наличии AI — третью.
6. Сохранить разметку и короткий отчёт об улучшениях/ошибках.

**Приёмка:** ноль нарушений условий; 100% источников подтверждены; объяснения выбранного режима проходят критерии `EVALUATION.md`. Не считать уникальность строк полноценной ручной оценкой. Автотесты выполнены; разметка ещё предстоит.

### T11 · Завершить воспроизводимость — P0, 1–2 ч, после T07/T10

**Действия:**

1. Проверить запуск из чистой папки проекта на Python 3.11/3.12.
2. Обновить снимки и убедиться, что их выдаёт реальный алгоритм.
3. Проверить ссылки документации и команды README.
4. Зафиксировать измерения отдельно от целевых SLA.
5. Подготовить CI; после размещения репозитория проверить фактический запуск workflow.

**Приёмка:** другой участник запускает проект по README, не обращаясь к автору. Локальные проверки есть; удалённый CI и отдельная машина пока не проверены.

### T12 · Провести защиту — P0, 1–2 ч, после T11

**Действия:**

1. Выполнить запрос плотной категории, объяснить различия трёх карточек.
2. Изменить только дату, показать причинную связь с календарём.
3. Показать редкую категорию и честные две карточки.
4. Показать оба типа пустоты.
5. По вопросу жюри открыть площадки и происхождение цены.
6. Повторить запрос и показать тот же порядок.
7. Объяснить пайплайн за 30 секунд.

**Приёмка:** сценарий занимает 4–5 минут; участники отличают то, что реализовано, от планируемого AI. Точный сценарий — `DEMO.md`.

## 4. Граф зависимостей

```text
T01 → T02 → T03 → T04 → T05 → T07 → T11 → T12
                 └────→ T06 ───┘       ↑
T02 + T05 → T08 → T09 → T10 ────────────┘
```

AI-ветка не должна блокировать работающее ядро. Если T08/T09 не успевают, T10 оценивает baseline и команда демонстрирует честный завершённый MVP.

## 5. Условия остановки и сокращения объёма

| Ситуация | Решение |
|---|---|
| До защиты <6 часов, API ещё не завершён | Закрыть T03–T07, использовать текущие extractive-объяснения |
| AI не даёт улучшения ручной оценки | Сохранить baseline основным режимом, показать эксперимент как эксперимент |
| Модель требует загрузки при каждом запуске | Подготовить артефакт заранее либо исключить зависимость из демо |
| Объяснения слишком похожи | Улучшать evidence/контраст, а не добавлять декоративные синонимы |
| Выдача часто пустая в декабре | Проверить правила и корректно объяснить сезонную занятость |
| Редкой категории не хватает до трёх | Показать фактическое количество и причину |
| Обнаружен конфликт описания и полей | Сохранить приоритет структурированных полей, не «исправлять» исходник под демо |

**Приоритет сокращения:** анимации/дизайн → онлайн-генерация → сложный ranker → дополнительные API-функции. Источники объяснений, календарь, три исхода и запуск по README остаются обязательными.

## 6. Карта дальнейшего развития

### После хакатона, 1–2 недели

- Перенести HTTP-адаптер на FastAPI с машинным контрактом.
- Добавить версионируемые обновления календарей и профилей.
- Ввести происхождение каждого добавленного профиля.
- Собирать оценки полезности объяснений и выбранного подрядчика.
- Добавить текст пожеланий как мягкий запрос, не как обход жёстких условий.
- Отдельно моделировать минимум часов, вместимость, пакет услуг и итоговую смету, если такие данные появятся.

### После появления реальной обратной связи

Сравнивать варианты объяснений на времени до решения, субъективной понятности, доле отказов из-за неожиданного нарушения условий. Обучать ранжирование только при наличии достаточной разметки; сохранять жёсткие проверки и источники вне обученной модели.

**Главная инженерная ставка:** развитие смысла и полезности объяснений поверх проверенного доменного ядра, а не усложнение инфраструктуры вокруг 66 записей.
