# Архитектурные решения и дальнейшее развитие

## ADR-001 · Источник истины — структурированные поля

**Контекст:** в описаниях есть города, языки и форматы, которые отличаются от подготовленных полей.

**Решение:** eligibility опирается на `city`, `categories`, `event_formats`, `languages`, `max_hours`, `price_from_kzt`, `busy_dates`. Описание даёт основания и мягкие признаки, но не переписывает условия.

**Следствие:** поведение воспроизводимо и соответствует схеме трека. Семантический слой не создаёт ложноположительные рекомендации при конфликте текста.

## ADR-002 · Полный перебор в памяти

**Контекст:** 66 профилей, 100 дней календаря.

**Решение:** валидировать и загрузить данные один раз, хранить календари множествами, использовать обычные списки и сортировку.

**Следствие:** нет внешней инфраструктуры для запуска. PostgreSQL или search-кластер можно добавить при регулярных обновлениях, большом количестве профилей и конкурентной записи; vector DB сейчас не обоснована объёмом.

## ADR-003 · Работающий baseline до AI-усиления

**Контекст:** хакатон оценивает живое поведение, объяснения и README; использование AI — часть технического критерия, но обучать модель на 66 профилях не требуется.

**Решение:** завершить reference core с открытым лексическим ключом и extractive-цитатами. AI интегрировать поверх, оценивая его реальный вклад в текст и порядок.

**Следствие:** текущая версия запускается без ключей. На защите честно обозначать rule-based baseline; техническое усложнение оправдывается измерением, а не названием технологии.

## ADR-004 · Офлайн признаки вместо онлайн агентного цикла

**Контекст:** каталог маленький и фиксированный; строгий детерминизм; задержка ориентировочно до 10 секунд.

**Решение для AI-итерации:** один подготовительный проход извлечения, проверяемые spans, сохранённые модели/промпты/hashes, заранее рассчитанные semantic scores. Онлайн — фильтрация и чтение артефакта.

**Следствие:** ошибка API не меняет порядок карточек; стоимость подготовки не повторяется на каждый запрос. Изменение описания требует инвалидации соответствующего артефакта.

Многошаговый agentic workflow не даёт очевидной пользы для фиксированной таблицы без внешних инструментов и действий. Его разумная будущая область — сбор недостающих параметров свободного запроса, но такой диалог не нужен обязательному сценарию трека.

## ADR-005 · Цитата — доказательство источника, не гарантия качества

**Контекст:** рекламные описания содержат самооценки, звания и непроверенные утверждения.

**Решение:** атрибутировать сведения профилю, хранить точный фрагмент, не превращать «лучший» и занятость в quality-score. Предпочитать факты об услуге, формате, стиле и составе.

**Следствие:** объяснение остаётся проверяемым и честным; для независимой проверки качества нужны другие данные.

## ADR-006 · Строгие условия не ослабляются ради заполнения выдачи

**Контекст:** редкие категории и декабрь закономерно дают мало или ноль вариантов.

**Решение:** возвращать фактическое число допустимых. Изменения даты/бюджета показывать отдельно, после реального пересчёта, без добавления неподходящих карточек.

**Следствие:** пустота превращается в понятный диагноз, а не маскируется расширением каталога.

## ADR-007 · Происхождение отдельно от ранга

**Контекст:** 13 synthetic, 18 price_imputed, 8 city_imputed; некоторые редкие категории зависят от синтетических записей.

**Решение:** использовать значения в фильтрах по правилам трека, явно показывать флаги, не вводить скрытый штраф.

**Следствие:** сохранено покрытие категорий и прозрачность. При добавлении командной синтетики понадобится манифест происхождения по ID; текущие метки рассчитаны на исходные 66 профилей.

## ADR-008 · Минимальный UI и HTTP-адаптер

**Контекст:** интерфейс имеет меньший приоритет, чем объяснения; среда должна запускаться быстро и без установки зависимостей.

**Решение:** стандартный локальный HTTP-сервер Python + одна HTML-страница. Доменное ядро изолировано.

**Следствие:** простое демо. При публичном запуске заменить адаптер на FastAPI/ASGI, добавить OpenAPI, таймауты и эксплуатационные метрики. Эта миграция не должна изменять смысл рекомендаций.

## ADR-009 · Артефакты и контрольные суммы в репозитории

**Контекст:** жюри должно воспроизвести результат на другой машине; Windows может менять LF на CRLF при checkout.

**Решение:** сохранить канонический JSONL, исходную контрольную сумму CSV, правила преобразования, снимки ответов, `.gitattributes` с LF для данных и кода.

**Следствие:** hash данных не зависит от стандартного checkout на Windows/Linux; изменения каталога легко обнаруживаются. Абсолютные пользовательские пути не зашиты в приложение.

## План пилота

| Условие роста | Следующий шаг | Что сохраняется |
|---|---|---|
| Каталог регулярно обновляется | Версионирование профилей и календаря, инвалидация evidence по hash | Приоритет полей и точные причины |
| Появляются свободные пожелания | Семантический brief как мягкий сигнал | Обязательные жёсткие ограничения |
| Нужна точная смета | Пакеты услуг, правила доплат, минимальные часы | Различие «от» и итоговой стоимости |
| Появилось число гостей | Структурированная вместимость и условия площадки | Не выводить вместимость из общей рекламы |
| Собрана обратная связь | Оценка helpfulness, pairwise preferences, обучение ranker | Фильтрация и источники вне модели |
| Тысячи/десятки тысяч профилей | Индексы по городу/категории, кэш, batch embeddings | Стабильный tie-break и аудит |

## Продуктовые метрики после появления пользователей

- Время до осмысленного выбора из трёх вариантов.
- Доля пользователей, понимающих причину рекомендации и отказа.
- Оценка полезности каждого объяснения.
- Частота обнаружения пользователем нарушения обязательных условий.
- Доля успешного изменения запроса после пустой выдачи.

CTR сам по себе недостаточен: привлекательная, но неподтверждённая формулировка может повышать клики и ухудшать качество выбора. Нужны одновременно ограничения корректности и оценка полезности.
